Claude Code 与 MCP：能力边界的三种说法

导入于 2026-10-31 14:02 · 2,140 字 · 37 个知识块 · sha256:9f2c…a71e
#001 · 412 tok · 文本

一、两种能力的定位

Claude Code 的 skill 是一段可被按需加载的说明与脚本集合，它的作用是让模型在特定任务上获得更稳定的行为；而 MCP server 是一个独立的进程，通过标准协议向客户端暴露工具、资源与提示模板。前者改变的是「模型知道什么、按什么步骤做」，后者改变的是「模型能访问什么外部系统」。

这个区分看起来只是概念问题，但在实际排障时会立刻分出高下：skill 出问题通常表现为行为不一致，MCP 出问题则表现为工具调用失败或根本不可见。

#002 · 538 tok · 文本

二、边界在哪里

把两者混为一谈，最常见的说法是「skill 也是一种工具，MCP 是工具的标准」。这句话有一半是对的：MCP 确实定义了工具的调用协议，但 skill 并不参与协议层。skill 更像是随任务分发的上下文包，它不要求宿主实现任何新的传输方式。

反过来，MCP server 也不负责告诉模型「什么时候该用它」。是否调用、按什么顺序调用，仍然由模型与系统提示决定。因此把 MCP 当成「会自动生效的能力」是一种误解。

#003 · 466 tok · 文本

三、实际取舍

如果需求是「让模型更可靠地完成一类任务」，优先考虑 skill：它不需要额外的服务，分发成本低，调试也简单。如果需求是「让模型访问外部系统」，那只能走 MCP，因为没有协议层就无法保证一次调用的结构、权限与错误能被正确处理。

两者并不互斥。一个常见的组合是：用 skill 描述任务流程，用 MCP 提供流程中需要的外部能力。

#004 · 198 tok · 文本

四、结论

把它们看成两个不同层次的东西，比争论「谁替代谁」更有用。skill 属于内容分发，MCP 属于能力接入。前者解决「怎么做」，后者解决「能做什么」。

Hybrid Retrieval

Technology · 最后更新 12 分钟前 · 最后审核 3 天前
已发布 可能过期 1 处未裁决
本页存在 1 处未裁决冲突
「默认召回数量」：来源《Qdrant 稀疏向量与混合检索实践》写的是 20，来源《RRF 参数调优笔记》写的是 50。

把向量检索与关键词检索的排名合并后再交给重排模型，用来同时覆盖「记得意思」与「记得字段名」两类查询。

它解决什么问题

单一路径都有硬缺陷。纯向量检索对专有名词、字段名、版本号不敏感，问「maxCharsPerRequest 这个字段叫什么」时召回的是语义相近但字段不同的段落；纯关键词检索又覆盖不了同义改写。

两路并行后，用倒数排名融合把结果合并，就能在不要求两路分数同量纲的前提下得到统一排序。

两路检索如何融合

RRF 只使用排名，不使用分数。对每个候选块计算 Σ 1/(k + rank)，k 通常取 60。这样即使一路是余弦相似度、另一路是 BM25 分数，也不需要做归一化。

融合之后再交给重排模型做精排。需要注意，重排只能改变顺序，不能改变候选集，否则「为什么这个块没出现」就无法解释。

代价与限制

两路检索意味着两套索引要维护，且中文关键词检索依赖分词质量。在分词效果不佳的语料上，关键词这一路的召回会明显低于向量路径，这时混合检索的收益主要来自专有名词的精确匹配。
