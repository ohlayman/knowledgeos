## 0. 这一版为什么值得单独做

V1 交付后，产品能回答「我的材料里有没有说过这件事」，但回答不了「关于这件事，我到底知道些什么」。

两者的差别不是措辞问题。V1 的答案是**若干段被检索到的原文拼接**，用户读到的仍是五份割裂的材料；V1.5 要给出的是**一个以概念为单位、随材料持续演进、每句话都能追到来源的页面**。这是产品从「检索工具」变成「知识系统」的分界线。

但这一版也最容易做坏。做坏的典型形态有三种，本文的规则基本都是为绕开它们而设：

**形态一：模型直接改页面。** 一旦允许，就再也说不清「这句是谁写的、依据什么、什么时候变的」。用户第一次发现页面内容与自己记忆不符时，就会失去对全部内容的信任。

**形态二：什么都合并。** 模型看到「RAG」和「GraphRAG」向量很近，就把两页并成一页。合并是不可逆的认知损失，比多一个待合并页面糟糕得多。

**形态三：冲突被抹平。** 两份材料说法不一致，模型习惯性地写出一段「既……又……」的平滑文字，把最有价值的信息——分歧本身——消掉了。

所以本文的核心不是「怎么生成页面」，而是**怎么让生成过程受控、可查、可退**。

## 1. 版本目标与交付边界

### 1.1 目标

导入一份新材料后，系统能自动判断它是否与已有知识相关，并产出**带证据、带冲突标记、待人工裁决的更新提案**；用户能在一次审核里看懂「改了什么、为什么改、依据在哪」，并安全地接受、拒绝或改写。

### 1.2 本版必须交付

| 能力 | 说明 |
| --- | --- |
| 知识抽取 | 从块中抽取实体、关系、事实，全部带来源块引用 |
| Wiki 编译 | 按概念生成页面，页面由「段落 + 证据锚点」组成 |
| 归属判定 | 新知识归属到已有页面 / 新建页面 / 忽略，三级判定 |
| 冲突检测 | 数值、否定、时间三类冲突，标记而不合并 |
| 更新提案 | 生成 diff、证据、冲突说明，进入待审队列 |
| 审核工作台 | 逐条或批量接受、拒绝、改写；支持 diff 对照 |
| 版本管理 | 每次落库生成 revision，可对照、可回滚 |
| 双向链接 | 页面之间可互跳，反链可查 |
| 过期提醒 | 来源被新版本替代时，页面标记「可能过期」 |
| 页面类型 | Concepts / Technologies / Projects / Comparisons / Research / Sources |

### 1.3 本版明确不做

不做图谱可视化、不做多跳检索、不做 Agent 编排、不做 MCP 对外接口、不做多人协作审核、不做页面级权限。

也不做「自动接受一切提案」的开关。审核策略可以分级，但**不存在全自动落库模式**，这是产品承诺，不是配置项。

### 1.4 与 V1 的关系

V1 的块模型与引用链路是 V1.5 的地基。具体依赖三件事：块能定位回原文、块带版本信息、引用可解析。任一不成立，Wiki 的证据锚点就是假的，页面也就不可信。

因此 V1.5 的开发启动条件是 V1 的 AC-M3-1、AC-M4-2、AC-M4-3 全部通过。

## 2. 增量数据模型

V1 已建立 `WikiPage`、`WikiRevision`、`WikiProposal` 三张表（见 V1 PRD 13.1）。本章补充字段要求与新增实体。

### 2.1 WikiPage

| 字段 | 要求 |
| --- | --- |
| `slug` | 全局唯一，规范化后生成（小写、连字符、去标点），中文标题保留原文并生成拼音或英文别名 |
| `type` | 六种页面类型之一，创建后不可改（改类型等于新建页面） |
| `status` | `draft` / `proposed` / `published` / `archived` / `stale` |
| `aliases` | 别名列表，供归属判定使用，**只能人工维护**，模型建议不自动写入 |
| `summary` | 一段不超过 120 字的摘要，由模型生成但必须人工确认后才对读者可见 |
| `sourceIds` | 该页面所有段落引用到的来源块集合（派生字段，用于回溯与过期检测） |
| `confidence` | 页面整体置信度：引用覆盖率 × 平均证据相关度，用于排序与筛选，不展示为百分比数字 |
| `lastReviewedAt` | 最近一次人工审核时间，`stale` 判定依赖它 |

### 2.2 WikiRevision

现有字段之外，必须增加：

- `editorType`：`model` / `human` / `system`（回滚产生）。
- `parentRevisionId`：形成版本链，回滚是「以旧内容新建版本」，不是删除后续版本。
- `changeSummary`：模型生成的一句话变更说明，人工编辑时手填，回滚时自动写。
- `diffStat`：新增/删除/修改的段落数，供列表展示。
- `proposalId`：若由提案落库产生，记录来源提案，便于追溯。

### 2.3 WikiProposal

| 字段 | 要求 |
| --- | --- |
| `targetPageId` | 更新提案必填；新建提案为空并携带拟建页面的完整内容 |
| `changeType` | `create` / `update` / `merge_suggestion` / `mark_stale` |
| `baseRevisionId` | 提案基于哪个版本生成。**这是防冲突的关键字段**：审核时若页面已有更新版本，提案必须重新校验 |
| `patch` | 段落级的最小变更集，不是整篇全文 |
| `evidence` | 每个变更段落对应的块 ID 列表 |
| `conflicts` | 冲突说明数组，含两个来源、各自表述、检测类型 |
| `validation` | 引用校验结果：通过 / 失败原因 |
| `status` | `pending` / `accepted` / `rejected` / `expired` / `invalid` |
| `reviewedBy` `reviewedAt` `rejectReason` | 审核留痕 |
| `modelMeta` | 模型名、提示版本、生成时间，供复盘 |

### 2.4 新增：Entity / Relation / Fact

| 实体 | 说明 |
| --- | --- |
| `Entity` | 名称、规范化名、类型（Concept / Technology / Project / Agent / Protocol）、别名、来源块集合、首次出现时间 |
| `Relation` | 起点实体、终点实体、关系类型（V1 PRD 8.6 的九种）、来源块、置信度 |
| `Fact` | 主体实体、谓词、值、来源块、采集时间、**文本身份标识**（用于判断同一事实的新旧版本） |

**约束：** 三者都必须至少挂一个来源块，否则不得入库。没有来源的实体和事实是纯模型幻觉，对产品只有负价值。

### 2.5 新增：ReviewTask（审核待办）

一条待办对应一个提案或一个过期页面。字段：类型（提案 / 过期复核 / 冲突裁决）、目标、优先级、创建时间、状态。

**为什么要独立建模而不是直接查提案表。** 因为「过期复核」和「冲突裁决」不是提案，但同样需要人的注意力。用一张表统一排队，用户只有一个「待办」入口，不必理解内部有几种对象。

## 3. 知识抽取

### 3.1 目标

把块变成可被检索、可被聚合、可被比对的结构化中间产物。抽取的产物**不是最终知识**，而是 Wiki 编译的原料。

### 3.2 抽取三类对象

**实体。** 规则：必须是稳定名词（Concept / Technology / Project / Agent / Protocol），必须有明确指代，必须至少在两处不同上下文中出现或来自两个不同来源，才进入候选集。单次出现的专名可能是笔误或临时说法，不足以建页。

**关系。** 规则：必须是九种关系类型之一，两端实体必须在同一块或相邻块中共现。**不允许模型自由发明关系类型**，新增类型需要改枚举并走版本发布。

**事实。** 规则：主体 + 谓词 + 值，值必须是可判定的（数值、布尔、版本号、明确断言），不接受「很重要」「比较好」这类评价性内容。

### 3.3 抽取的输入与输出

输入为单个块的文本 + 上下文窗口（前后各一块）+ 已有实体词典（用于对齐）。

输出为结构化 JSON，必须通过 Schema 校验：

```text
{
  entities: [{ name, type, aliases[], evidenceChunkId }],
  relations: [{ from, to, type, evidenceChunkId, confidence }],
  facts: [{ subject, predicate, value, evidenceChunkId }]
}
```

**Schema 校验失败时的处理：** 重试一次；仍失败则丢弃该块的抽取结果并记录，**不阻断文档整体处理**。一个块的抽取失败不应该让整份文档不可用。

### 3.4 实体对齐

同一实体在不同材料里可能有多种写法（「混合检索」「Hybrid Retrieval」「hybrid search」）。对齐规则：

其一，**精确匹配优先**：规范化后（去空格、统一大小写、去复数）与已有实体名或别名相同。

其二，**别名表其次**：人工维护的别名映射。

其三，**向量相似 + 类型一致**才允许建议合并，且只生成「合并建议」交人工处理，**不自动合并**。

**对齐失败时宁可新建。** 两个实体的错误合并会污染后续所有关系与页面，成本远高于多一个重复实体。

### 3.5 成本与预算

抽取是逐块调用模型，成本与文档量线性相关。要求：

- 单文档抽取预算上限可配置（按 token 计），超额时降级为「只抽实体，不抽关系与事实」。
- 抽取结果按 `(块ID, 模型版本)` 缓存，重跑同一块不重复计费。
- 批量导入时抽取任务与 V1 的向量化任务分队列，避免互相阻塞。

## 4. Wiki 编译

### 4.1 页面结构与「段落-证据」绑定

一个 Wiki 页面不是一整段 Markdown，而是**有序的段落集合**，每段有自己的标识与证据锚点。

```text
Page
 ├─ summary          摘要（人工确认后可见）
 ├─ section[]        章节
 │    └─ paragraph[] 段落（最小编辑单元）
 │         ├─ text
 │         ├─ evidenceChunkIds[]  至少一个
 │         ├─ origin: model | human
 │         └─ versionIntroduced
 └─ relatedPageIds[]
```

**为什么以段落为最小单元。** 三个理由：diff 需要段落级对照，否则长页面不可读；审核需要按段接受或拒绝；人工编辑过的段落需要被单独保护，不被模型覆盖。整页级的版本管理做不到这三点。

### 4.2 页面模板

| 类型 | 结构 | 典型长度 |
| --- | --- | --- |
| Concepts | 定义 → 工作原理 → 与其他概念的关系 → 常见误解 → 来源 | 800–1600 字 |
| Technologies | 是什么 → 解决什么问题 → 核心能力 → 限制与代价 → 替代方案 → 来源 | 1000–2000 字 |
| Projects | 定位 → 架构 → 关键设计 → 适用场景 → 来源 | 800–1500 字 |
| Comparisons | 对比维度表 → 逐项差异 → 选型建议 → 来源 | 600–1200 字 |
| Research | 问题 → 方法 → 结论 → 局限 → 来源 | 800–1500 字 |
| Sources | 来源清单与索引，由系统生成，不允许模型撰写正文 | — |

模板的作用是**约束模型的输出结构**，不是装饰。没有模板时模型倾向于写成散文，段落无法对应到固定语义，后续的增量更新就失去了挂载点。

### 4.3 编译流程

```text
触发：文档处理完成（或用户手动「重建 Wiki」）
  → 1 收集该文档产生的实体、事实、关系
  → 2 对每个候选实体做归属判定（见第 5 章）
  → 3 命中已有页面：取出该页面当前版本作为编译上下文
  → 4 生成变更提案（新增段落 / 修改段落 / 标记冲突）
  → 5 引用验证（每段至少一个可解析证据）
  → 6 冲突检测与标注
  → 7 写入 Proposal，进入待审队列
```

**触发策略。** 不允许「每导入一份文档就全量重建所有页面」——成本不可控且会产生大量噪声提案。规则：单次导入只处理与本文档实体相关的页面，且同一页面在 10 分钟内的多次触发合并为一次编译。

### 4.4 生成规则

其一，**一段一断言。** 每个段落只表达一个可被证据支持的主张。多主张混在一段里，审核者无法逐条接受或拒绝。

其二，**贴近原文措辞。** 优先改写而非重写，保留原文的限定词（「在某些版本中」「通常」「不建议」）。这些限定词是技术材料的价值所在，模型倾向于删掉它们让句子更顺。

其三，**不确定就标注。** 当证据只支持部分论断时，段落末尾必须标注「证据不足以覆盖全部论述」，而不是补齐一个看起来完整的句子。

其四，**不引入证据之外的信息。** 包括不补充背景、不解释常识、不举例。页面是材料的组织，不是教程。

其五，**段落数上限。** 单页不超过 12 个段落，超出时拆分页面或合并同义段。页面过长说明这个概念需要被拆成多个概念。

### 4.5 输出校验

提案落库前必须通过：

| 检查 | 规则 | 失败处理 |
| --- | --- | --- |
| Schema | 结构符合段落模型 | 重试一次，仍失败标记 invalid |
| 引用存在 | 所有 `evidenceChunkIds` 真实存在 | 标记 invalid，不进入队列 |
| 引用支持 | 段落内容与证据块语义一致（模型二次判定 + 关键词重合度） | 标记 invalid 并记录原因 |
| 无凭空生成 | 段落中的专有名词与数值必须在证据中出现 | 标记 invalid |
| 长度 | 段落 80–400 字，页面 600–2400 字 | 超限截断或拆分，记录 |

**「引用存在」与「引用支持」是两件事。** 前者是数据库查询，后者是语义判断。只做前者的话，模型可以随便挂一个存在的块 ID 来通过校验。

## 5. 归属判定

### 5.1 三级判定

对每个候选实体，依次尝试：

**第一级：显式匹配。** 与页面的 `slug`、`title`、`aliases` 精确匹配（规范化后）。命中即归属，不再往下判断。

**第二级：强结构匹配。** 实体名与页面标题的编辑距离小于阈值，**且**实体类型与页面 `type` 一致，**且**该实体已在页面的证据块中出现过至少一次。三者同时满足才归属。

**第三级：语义匹配。** 向量相似度高于阈值，**且**共享至少一个来源，**且**实体类型一致。满足才归属。

**不满足任何一级：新建页面提案。**

### 5.2 为什么阈值要三条件而不是单看相似度

单看相似度会出两类错误：把「RAG」并入「GraphRAG」（相似但不同层级），把「Qdrant」并入「向量数据库」（个体与类别）。加上类型一致与来源共享两个条件，能挡掉大部分这类错误。

**遗留风险：** 同类型、共享来源、语义相近但确实不同的两个概念仍可能被误并。这类错误无法靠规则完全消除，只能靠「宁可新建」的默认倾向 + 人工合并入口来兜底。

### 5.3 合并建议而非自动合并

当判定「可能属于同一页面」但未达归属阈值时，生成 `merge_suggestion` 提案，附上两个页面的差异摘要，交人工处理。**系统永不自动合并两个已发布页面。**

### 5.4 判定记录

每次判定必须记录：候选实体、尝试过哪几级、各级得分、最终结论。这份记录在审核界面的「为什么归到这里」里可见。

**这是可解释性的最低要求。** 用户看到一个页面被更新，至少要知道系统凭什么认为这是同一个概念。

## 6. 冲突检测

### 6.1 三类信号

| 类型 | 例子 | 检测方式 |
| --- | --- | --- |
| 数值冲突 | 一处说「默认 60 秒」，另一处说「默认 30 秒」 | 抽取 facts 后比对同主体同谓词的值 |
| 否定冲突 | 一处说「支持稀疏向量」，另一处说「不支持」 | 同谓词下的极性判断 |
| 时间性差异 | 一处描述 v1 行为，另一处描述 v2 行为 | 来源版本 / 文档发布时间 |

### 6.2 处理规则

其一，**冲突不合并。** 提案里并列两段，各自挂来源，中间用冲突标记连接。

其二，**时间性差异优先按版本呈现，不判对错。** 页面里写成「v1 中为 X，v2 中变更为 Y」——技术材料的价值恰恰在演变过程里。

其三，**跨来源冲突不按时间裁决。** 两位作者的表述没有先后关系，交给人工。

其四，**未裁决冲突在页面上可见。** 页头显示「本页存在 1 处未裁决冲突」，读者点开能看到双方说法。**隐瞒冲突等于系统替用户做了判断。**

### 6.3 冲突的生命周期

`detected` → `pending_review` → `resolved_keep_a` / `resolved_keep_b` / `resolved_merge` / `dismissed`。

任何一次裁决都要记录裁决人、时间、理由（可选但鼓励填写）。裁决后页面上的冲突标记消失，但裁决记录永久保留在版本历史里。

## 7. 审核工作台

### 7.1 队列设计

一个入口，三类对象：待审提案、过期复核、冲突裁决。默认按「影响面 × 时间」排序——影响面指该页面被引用次数与最近访问量。

**不按创建时间排序。** 一条涉及高访问页面的提案，比十条冷门页面的提案更值得先看。

### 7.2 单条审核的界面要求

审核者需要在**一屏之内**回答四个问题：

1. 改了什么？（段落级 diff，新增/删除/修改用不同底色）
2. 依据是什么？（每个变更段落旁挂证据，点击可看原文）
3. 有没有争议？（冲突标记与双方来源）
4. 改完会不会破坏已有内容？（显示受影响的其他段落与反链）

如果这四个问题需要翻页或开新窗口才能回答，审核就会退化成盲签。

### 7.3 三种操作

| 操作 | 效果 |
| --- | --- |
| 接受 | 按 patch 落库，生成新 revision，`editorType=model`，记录提案 ID |
| 拒绝 | 提案置 `rejected`，必填拒绝原因（从预设选项选，可补充文字） |
| 改写后接受 | 打开编辑器，预填提案内容，用户修改后落库，`editorType=human` |

**拒绝原因必须结构化。** 预设选项：事实错误 / 证据不足 / 与已有内容重复 / 归属错误 / 表述不当。自由文本作为补充。没有结构化原因，后续无法统计哪类提案质量差、无法改进提示词。

### 7.4 批量操作

允许批量接受同类低风险提案（例如同一文档产生的纯新增段落提案），但：

- 批量操作前显示将被修改的页面清单。
- 涉及删除或修改已发布段落的提案**不得批量接受**。
- 批量接受后仍逐条记录审核痕迹。

### 7.5 审核冲突

若审核时页面已产生新版本（`baseRevisionId` 落后），提案不能直接落库。系统需重新生成针对最新版本的 patch，并提示「该提案基于旧版本，已重新计算差异」。若重新计算失败，提案置 `invalid` 并说明原因。

**这条最容易被忽略，但它是并发编辑下数据正确性的唯一保障。**

### 7.6 审核的时效

提案超过 14 天未处理自动置 `expired`，不再出现在主队列，但可在「已过期」筛选中恢复。过期不等于删除，用户仍可查看当时的完整提案。

## 8. 版本、回滚与过期

### 8.1 版本

每次落库生成新 revision，永不覆盖。revision 列表需展示：版本号、编辑者类型、变更摘要、时间、diff 统计。支持任意两版对照。

### 8.2 回滚

回滚 = 以目标版本内容创建一个新版本。因此：

- 历史链完整，回滚本身也可被回滚。
- 回滚不删除中间版本。
- 回滚需填写原因。

### 8.3 过期提醒

触发条件：页面引用的某个来源块所属文档产生了新版本，且新版本中该块内容发生变化。

处理：页面状态置 `stale`，生成一条「过期复核」待办，页面顶部显示提示条。**不自动修改页面内容**——来源更新不等于页面结论过时，需要人判断。

复核动作三种：确认仍有效（清除 stale，记录复核时间）、按新来源更新（生成提案）、归档页面。

### 8.4 归档

`archived` 页面不参与检索、不出现在默认列表、但保留全部版本与反链。归档不是删除。

---

## 9. 双向链接

### 9.1 链接的产生

两种来源：模型在编译时识别到的概念提及（`[[slug]]` 形式），以及人工编辑时手动插入。

### 9.2 链接的约束

其一，**只链接到存在的页面。** 指向不存在页面的链接显示为「待创建」，点击可发起新建提案，不显示为坏链。

其二，**链接必须能让读者理解关系。** 裸链接（只有页面名）不如带类型的链接（「依赖 → Hybrid Retrieval」）。V1.5 允许关系类型作为可选修饰。

其三，**反链自动维护**，不需要人工登记。

### 9.3 反链面板

页面底部固定展示「被以下页面引用」，每条含来源页面名与该处的上下文一句。**反链是 Wiki 相对普通文档最有价值的部分**，它让用户看到知识的使用场景，而不只是定义。

## 10. 页面信息架构增量

在 V1 的导航上新增一项「Wiki」，下分三个视图：

```text
/wiki                 页面树 + 阅读
/wiki/:slug           页面阅读
/wiki/:slug/edit      编辑（人工）
/wiki/:slug/history   版本对照
/wiki/review          审核队列
/wiki/review/:id      单条提案详情
/wiki/conflicts       冲突裁决列表
```

「待审核」的数量以徽标形式挂在 Wiki 导航项上，**超过 20 条时显示 `20+`**，避免数字过长挤压布局。

## 11. 接口增量

| 资源 | 能力 | 说明 |
| --- | --- | --- |
| 页面 | 列表（按类型/状态）、详情、创建、编辑、归档 | 编辑直接产生 revision |
| 版本 | 列表、详情、两版对照、回滚 | 对照返回段落级 diff |
| 提案 | 列表（按状态）、详情、接受、拒绝、改写后接受 | 接受需携带 `baseRevisionId` |
| 冲突 | 列表、裁决 | 裁决需记录结论与理由 |
| 实体 | 列表、详情、合并建议 | 合并需人工确认 |
| 抽取 | 按文档触发、查看结果 | 幂等，按块缓存 |

**关键约束：** 所有写操作必须携带 `baseRevisionId` 或 `etag`，服务端校验版本一致性。这是防止「基于旧版本覆盖新内容」的唯一手段。

## 12. 非功能性要求

**生成预算。** 单次编译的 token 上限可配置；超出时只生成新增段落，不做全文重写。

**批处理。** 同一页面的多次触发在 10 分钟窗口内合并；合并期间页面显示「有更新待编译」。

**幂等。** 同一文档版本对同一页面的编译结果必须一致；重复触发不产生重复提案（以 `(文档版本, 页面, 提案类型)` 去重）。

**延迟。** 从文档处理完成到提案出现在队列，P95 ≤ 5 分钟。这是异步任务，不要求实时。

**可观测。** 每条提案的生成耗时、token 消耗、校验结果、审核耗时都要记录，用于评估这套机制的实际收益。

**数据安全。** 提案与版本中不得包含超出证据块的原文片段；导出时包含完整版本链。

## 13. 验收标准

- AC-V15-1：导入一篇与已有页面主题相同的新材料，系统生成更新提案而非新页面，提案含段落级 diff 与至少一条可解析证据。
- AC-V15-2：构造两份说法矛盾的材料，提案中出现冲突标记，页面在裁决前显示「存在未裁决冲突」。
- AC-V15-3：删除提案引用的块后，该提案在进入队列前被拦截，状态为 `invalid` 并记录原因。
- AC-V15-4：页面回滚到三版之前，内容正确、历史完整，且回滚动作本身产生新版本。
- AC-V15-5：人工编辑过的段落，模型提案不得覆盖；提案中该段落显示为「受保护，需显式解锁」。
- AC-V15-6：审核时若页面已被他人更新，接受操作被拒绝并提示重新计算差异。
- AC-V15-7：拒绝提案必须选择结构化原因，未选择时提交被阻止。
- AC-V15-8：来源文档更新后，引用它的页面在 5 分钟内标记为 `stale`，并生成复核待办。
- AC-V15-9：抽检 20 个页面，每个非导语段落至少有一个证据锚点，点击可定位到原文。
- AC-V15-10：页面反链在对方页面新增引用后 1 分钟内自动出现。
- AC-V15-11：同一文档版本重复触发编译，不产生重复提案。
- AC-V15-12：单页超过 12 段时，系统提示拆分而不是继续生成。

## 14. 风险

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| V15-R1 | 归属判定错并概念 | 知识被污染且难以察觉 | 三级判定 + 宁建新页；合并只建议不执行 |
| V15-R2 | 提案量爆炸，审核成瓶颈 | 用户放弃审核，退回全自动 | 影响面排序、批量接受低风险项、限制单次编译范围 |
| V15-R3 | 抽取成本超预期 | 单文档成本翻倍 | 按块缓存、预算上限、降级策略 |
| V15-R4 | 模型改写丢失限定词 | 技术结论被绝对化 | 提示词要求贴近原文 + 审核时高亮限定词被删除的位置 |
| V15-R5 | 页面越写越长 | 失去可读性 | 段落上限 12，超出提示拆页 |
| V15-R6 | 过期误判 | 大量无效待办 | 只有块内容实际变化才触发，不是文档版本变化就触发 |
