# V3 MCP 外部可用性报告

> 生成日期：2026-11-01。样本来自本机验收运行与设置页探针，不代表真实用户长期使用。

## 1. 结论

**协议层可用：** 13 次经审计的工具调用全部成功，平均耗时 75ms；作用域、吊销、限流与截断都在真实请求上触发过。

**真实客户端采用率尚未测量：** 目前验证的是官方 MCP SDK 的 stdio 客户端与设置页探针，不是 Claude Code / Cursor 里的真实编码会话。因此本报告只能回答「接口能不能用」，还不能回答「Agent 会不会主动用」。

## 2. 样本与方法

| 项 | 值 |
| --- | --- |
| 执行方式 | `scripts/acceptance-v3.mjs` 用 MCP SDK stdio 客户端拉起 `apps/mcp-server/dist/index.js` |
| 场景 | 检索「RRF 参数」、读取 Wiki 页面、查询来源、问答、提交更新提案 |
| 调用次数 | 13 |
| 成功次数 | 13 |
| 失败次数 | 0 |
| 平均延迟 | 75ms（审计表 `duration_ms`） |

按工具分布：

| 工具 | 次数 |
| --- | --- |
| `search_knowledge` | 8 |
| `propose_knowledge_update` | 2 |
| `read_wiki` | 1 |
| `get_knowledge_sources` | 1 |
| `ask_knowledge` | 1 |
| `get_related_knowledge` | 0（验收未构造实体路径样本） |

## 3. 它为什么可能不用

以下判断来自接口行为与工具描述，不是真实会话统计。

1. **工具太多会稀释选择。** 六个工具里，编码任务最常用的是 `search_knowledge`；`ask_knowledge` 慢且返回长文本，`get_related_knowledge` 需要实体 ID。工具描述如果都写成「查询知识」，Agent 会随机挑一个。
2. **空结果最容易被误判为失败。** 本次验收特意覆盖了 `no_match_in_scope`；如果客户端把空数组当成「服务坏了」，会重试或放弃，而不是换关键词。
3. **作用域令牌会让结果变少。** 限标签令牌检索不到范围外内容，这是正确行为；但 Agent 看不到范围，容易以为知识库没有相关内容。
4. **配置摩擦发生在第一次使用。** 需要填写 API 地址、令牌、可执行文件路径，非 Windows 还要 `chmod 600`；任何一项错了都表现为「工具不可用」。
5. **不可信内容警告可能让 Agent 变保守。** 返回 Markdown 前的提示语会让部分客户端只做摘要、不引用原文；这是安全与可用性的取舍。
6. **`ask_knowledge` 的 8 秒级延迟** 在交互式编码中偏慢，Agent 更倾向于先 `search_knowledge`。

## 4. 建议

- 在接入文档中给出一句话用法：「查资料先 `search_knowledge`，需要成段解释再 `ask_knowledge`」。
- 空结果文案保持「没有找到」而不是错误，并附 `reason`；已实现。
- 作用域令牌在设置页显示「约 N 份文档可被访问」；当前仅显示标签/数量，后续可补真实文档数。
- 用 `get_knowledge_sources` 让 Agent 能解释「这条结论来自哪份文档」，提高引用意愿。
- 真实采用率需要下一轮验证：在 Claude Code / Cursor 中完成 5 个真实编码任务，记录「是否调用、第几次调用、是否采用返回内容」。

## 5. 下一步

1. 用户按 `ACCEPTANCE_V3.md` 第 5 节粘贴配置，完成 Claude Code 与 Cursor 各一次真实会话。
2. 统计真实会话中的工具选择与放弃原因，补一份带会话记录的报告。
3. 若 `ask_knowledge` 延迟成为主要阻碍，再评估流式返回或缩短答案长度。
