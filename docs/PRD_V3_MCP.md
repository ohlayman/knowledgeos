## 0. 定位：这不是一个新系统

MCP Server 是同一套检索能力对外的第二个出口。这句话决定了三件事：

**其一，它不在 MCP 进程里重新实现检索。** MCP 进程只做协议适配：接收工具调用、转换参数、调用内部 API、把结果转成 MCP 的返回格式。检索、权限、审计全部复用 API 层。

**其二，它不能有独立的权限模型。** 如果 MCP 自己判断「这个令牌能看到哪些文档」，那么同一个用户在网页和 MCP 里会看到不同的东西，而这种不一致极难排查。

**其三，它的质量上限由 V1 决定。** 如果检索召回不好，MCP 只是把这个缺点暴露给外部 Agent，而且用户看不见过程，更难发现问题。

### 0.1 为什么值得做

因为它改变了产品的使用位置。没有 MCP 时，用户必须切到 KnowledgeOS 的网页问一次，再把答案复制到编辑器里；有了 MCP，Agent 在写代码的过程中就能查到「我三个月前记的那条参数」。**知识的价值在于被用到的时刻，而不是被收藏的时刻。**

## 1. 版本目标与边界

### 1.1 必须交付

| 能力 | 说明 |
| --- | --- |
| 六个 MCP 工具 | 五个只读 + 一个提案（默认关闭） |
| 令牌与作用域 | 标签/文档集合、工具白名单、额度、有效期 |
| 审计 | 每次调用留痕，不记录正文 |
| 限流 | 令牌级 QPS 与日调用上限 |
| 传输 | 本地 stdio 优先，HTTP 远程后置 |
| 接入指引 | Claude Code / Cursor 的配置片段 |

### 1.2 明确不做

不做写入工具；不做 MCP 的 OAuth 授权流程（V4 以后再评估）；不做多租户；不做 MCP 侧的独立缓存（缓存会绕过权限变更）。

## 2. 传输形态

### 2.1 两种形态

| 形态 | 适用 | 说明 |
| --- | --- | --- |
| **stdio（V3 首发）** | 本机使用 | MCP 客户端拉起本地进程，通过标准输入输出通信 |
| **HTTP（V3 后半）** | 远程/多设备 | 需要认证与 TLS，承担公网暴露风险 |

**先做 stdio。** 目标用户是个人开发者，知识库本就在本机；stdio 不需要处理公网暴露、TLS、跨域、反向代理，风险面积小一个数量级。

### 2.2 stdio 模式下的令牌

即使是本地进程，**仍然需要令牌**，不允许「本机即全权限」的隐式提权。

原因：本地进程默认拥有全部权限的话，任何能写配置文件的东西都能读走整个知识库；而令牌可以限定作用域、可以吊销、可以审计。

令牌从配置文件读取（路径由客户端配置传入），文件权限要求 600，启动时校验。

### 2.3 HTTP 模式的额外要求

必须 TLS；必须校验 Origin；必须限流；必须支持令牌吊销后的即时失效（不使用长连接缓存）。

## 3. 工具契约

### 3.1 六个工具

| 工具 | 类型 | 用途 | 默认 |
| --- | --- | --- | --- |
| `search_knowledge` | 只读 | 语义 + 关键词混合检索 | 开启 |
| `read_wiki` | 只读 | 读取已发布 Wiki 页面 | 开启 |
| `get_related_knowledge` | 只读 | 图谱邻域（V2 能力） | 开启 |
| `get_knowledge_sources` | 只读 | 查块/文档的来源元数据 | 开启 |
| `ask_knowledge` | 只读 | 完整问答（含引用） | 开启 |
| `propose_knowledge_update` | 提案 | 创建 Wiki 更新提案，**不落库** | **关闭** |

### 3.2 输入与输出

| 工具 | 关键输入 | 输出要点 |
| --- | --- | --- |
| `search_knowledge` | `query`（必填）、`topK`（默认 8，上限 20）、`scope`（可选标签/文档 ID） | 片段数组：文本、文档标题、文档 ID、块 ID、位置、相关度 |
| `read_wiki` | `slug` 或 `pageId`、`version`（可选） | 标题、类型、正文 Markdown、版本号、最后更新 |
| `get_related_knowledge` | `entityId` 或 `pageId`、`hops`（默认 1，上限 2） | 关联项数组：实体名、关系类型、方向、证据数 |
| `get_knowledge_sources` | `chunkId` 或 `documentId` | 来源类型、导入时间、文档版本、原始链接（若有） |
| `ask_knowledge` | `question`、`scope` | 回答、引用数组、`hasSufficientEvidence` 布尔 |
| `propose_knowledge_update` | `pageId`、`summary`、`evidenceChunkIds` | 提案 ID、状态（`pending`） |

### 3.3 输出原则

**结构化优先。** 每个工具都返回可直接解析的字段，而不是一段自然语言。文本片段额外附一段 Markdown 便于人读，但结构化字段是主。

**空结果不报错。** 作用域内没有内容时，返回空数组 + `reason`（如 `no_match_in_scope`）。**不要用错误表达「没找到」**，外部 Agent 无法区分「失败」和「没有」。

**必须带溯源。** 任何文本片段都要附文档 ID 与块 ID，客户端才能自行引用。

**不返回全文。** `search_knowledge` 只返回片段，不返回整篇文档；需要全文请用 `read_wiki`（已发布页面）或后续的块接口。

### 3.4 错误契约

| 情况 | 返回 |
| --- | --- |
| 参数缺失或类型错误 | 参数错误，附一个合法示例 |
| 令牌无权调用该工具 | 权限错误，**且不暴露该工具是否存在** |
| 令牌过期或吊销 | 认证错误，附重新配置指引 |
| 作用域内无数据 | 成功，空结果 + 原因 |
| 上游检索超时 | 服务不可用，标记为可重试 |
| 结果被截断 | 成功，附 `truncated: true` 与原始条数 |

## 4. 令牌与作用域

### 4.1 令牌结构

令牌由「前缀 + 随机串」组成，前缀用于识别类型（如 `kos_`），随机串 32 字节。

**只存哈希。** 数据库存 `sha256(token)`，明文只在创建时返回一次。之后任何时候都无法再次查看，只能吊销重建。

### 4.2 作用域维度

| 维度 | 说明 | 默认 |
| --- | --- | --- |
| 文档范围 | 全部 / 指定标签 / 指定文档集合 | 全部 |
| 工具白名单 | 六个工具的子集 | 五个只读 |
| 每日调用上限 | 次数 | 500 |
| QPS 上限 | 每秒请求数 | 5 |
| 有效期 | 到期自动失效 | 90 天 |

### 4.3 作用域在检索阶段生效

**这是本节最重要的一条。** 作用域必须在**检索请求发出时**就作为过滤条件下推，而不是先查出结果再在返回前过滤。

原因有二：先查后滤会让越权内容进入进程内存与日志，泄露面变大；而且过滤后的条数会少于客户端请求的 topK，结果质量下降却看不出原因。

### 4.4 令牌管理接口

创建、列表（不含明文）、吊销、更新作用域。**吊销即时生效**，不使用长连接缓存。

## 5. 审计与限流

### 5.1 审计记录

每次调用记录：时间、令牌 ID（不是明文）、工具名、参数摘要、返回条数、耗时、状态码、请求来源（stdio / HTTP）。

**不记录返回正文。** 审计日志一旦包含正文，它本身就成了第二个数据泄露面，而且体积会失控。

**参数摘要要脱敏**：查询词可以记录（用于分析检索质量），但任何疑似密钥的字段替换为占位符。

### 5.2 限流

令牌级 QPS 与日上限双重限制。触发时返回可重试错误，并附恢复时间（对于日上限，是次日 00:00；对于 QPS，是建议重试的毫秒数）。

**限流的目的是保护本地资源与上游配额，不是防滥用。** 单用户场景下，滥用风险来自客户端 bug（例如 Agent 循环调用），而不是恶意。

### 5.3 可观测

面板展示：今日调用次数、按工具分布、失败率、平均延迟、被限流次数。数据来自审计表，不做额外埋点。

## 6. 安全

### 6.1 三个必须防的东西

**令牌泄露。** 明文只显示一次；配置文件权限 600；吊销即时生效；日志中不出现明文。

**作用域绕过。** 过滤在检索阶段下推；`read_wiki` 只能读 `published` 且在当前作用域内的页面；`get_related_knowledge` 的邻居若超出作用域则不返回。

**提示注入的回流。** 这是 MCP 特有的风险：知识库里的文档可能含有「忽略之前的指令」这类文本，经 MCP 返回给外部 Agent（如 Claude Code）后，可能影响外部 Agent 的行为。

处理原则：

- 返回内容中，来自文档的文本一律包装为**引用数据**，并在字段名上体现（如 `excerpt`），不混入指令区。
- 对已知的注入模式做标记（`suspicious: true`），但**不阻断返回**——阻断会误伤正常技术文档。
- 文档中明确告知用户：KnowledgeOS 不保证所返回内容不含对抗性文本，客户端应自行把工具返回视为不可信输入。

**这条必须写进接入文档。** 我们不能替外部 Agent 做安全决策，但必须让使用者知道风险存在。

### 6.2 权限模型的位置

权限判断只在 API 层做一次。MCP 进程不做权限判断，只透传令牌。

**为什么强调这一点。** 两处判断迟早会不一致，而不一致的安全判断比没有判断更危险——因为你以为它管住了。

## 8. 客户端兼容

### 8.1 目标客户端

Claude Code（stdio）、Cursor（stdio）。HTTP 模式兼容支持远程 MCP 的客户端。

### 8.2 兼容性要求

**工具描述要写清适用场景。** 外部 Agent 靠描述决定调不调用；描述含糊会导致它不用，或者用错。

**输出体积要可控。** 单个工具返回的文本总量上限 32KB，超出截断并标记。**不要让一次工具调用撑爆客户端上下文**——这是 MCP 集成最常见的翻车方式。

**幂等。** 只读工具必须幂等；`propose_knowledge_update` 在同一页面同一证据集上重复调用应返回已有提案，不重复创建。

### 8.3 接入片段

为每个客户端提供可直接复制的配置片段，包含：命令、参数、令牌环境变量的设置方式、以及一句「令牌需自行替换」的提示。

## 9. 非功能要求

| 项 | 要求 |
| --- | --- |
| `search_knowledge` 延迟 | P95 ≤ 800ms |
| `ask_knowledge` 首 token | 不要求流式，整体 P95 ≤ 8s |
| 单次返回体积 | ≤ 32KB，超出截断并标记 |
| 审计写入 | 异步，不阻塞响应 |
| 令牌校验 | ≤ 5ms |
| 可用性 | 上游不可用时，错误要在 2s 内返回，不挂起 |

## 10. 验收

- AC-V3-1：在 Claude Code 中配置 stdio 后，`search_knowledge` 返回真实片段，且每条附文档 ID 与块 ID。
- AC-V3-2：用限定标签的令牌调用，结果不含作用域外文档；且在检索日志中能看到过滤条件已下推。
- AC-V3-3：吊销令牌后，下一次调用立即失败，不因缓存继续可用。
- AC-V3-4：令牌明文只在创建时出现一次，之后任何接口都不返回明文。
- AC-V3-5：`propose_knowledge_update` 只创建提案；审核前 Wiki 页面内容不变。
- AC-V3-6：作用域内无结果时返回空数组与原因，不返回错误。
- AC-V3-7：单次返回超过 32KB 时被截断并标记 `truncated`。
- AC-V3-8：审计记录包含工具、条数、耗时、令牌 ID，但**不包含返回正文**。
- AC-V3-9：日调用上限触发后返回带恢复时间的错误；次日恢复。
- AC-V3-10：文档中植入提示注入文本时，返回结果标记 `suspicious`，且不影响工具本身的行为。

## 11. 风险

| 编号 | 风险 | 影响 | 应对 |
| --- | --- | --- | --- |
| V3-R1 | 令牌泄露 | 知识库被外部读取 | 只存哈希、显示一次、可吊销、配置文件 600 |
| V3-R2 | 作用域绕过 | 越权读取 | 过滤下推、邻居过滤、read_wiki 只读已发布 |
| V3-R3 | 返回内容撑爆客户端上下文 | 外部 Agent 崩掉 | 32KB 上限 + 截断标记 + 工具描述写明体积 |
| V3-R4 | 外部 Agent 把返回内容当指令 | 提示注入回流 | 包装为引用数据、标记可疑、接入文档写明 |
| V3-R5 | 与网页端权限不一致 | 难以排查的差异 | 权限只在 API 层判断，MCP 不判断 |
| V3-R6 | 客户端兼容差异 | 部分客户端用不了 | 首选 stdio；工具描述与输出格式贴近 MCP 规范；按客户端做接入验证 |

## 12. 交付清单

六个工具的实现；令牌与审计；stdio 与 HTTP 两种形态；两份客户端接入验证记录（Claude Code、Cursor）；以及一份**外部可用性报告**——在真实编码任务中，外部 Agent 调用本服务的成功率与「它为什么不用」的分析。**没有这份报告，无法判断这套接口是有人用，还是只是做完了。**
